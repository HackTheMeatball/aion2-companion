## 1. What ships

| # | Element | Where | Basic | Full |
|---|---|---|---|---|
| 1 | "Last backup" line | the existing footer export row (`#xfer`), on its own line after "Progress is saved in this browser only." | yes | yes |
| 2 | Export nudge | one slim card under the header, above the layout (same slot and layout as `#saveWarn`) | yes | yes |
| 3 | Add to Home Screen hint | the same card slot as 2 | yes | yes |

All three are **standalone site only, never in the claude.ai build** (ROADMAP 0.1.x "Save safety": "Never in the
claude.ai build", which covers the whole bullet). Their markup sits in `@web-only` blocks, so `dist-artifact` does not
contain it, and the logic lives with the site's own script, like `src/site.js` (`window.claude` present = no UI either).
The storage side (§4: the `backup` field, the `backup1` step, the import rule) is shared code and runs in both builds; in
the claude.ai build it only records times nothing reads, which is harmless and keeps one save shape.

No new card type, no new section, no extra row in the rail. The nudge and the hint reuse one card layout
(`.card.nudge`: one row, text left, buttons right, wraps on phones). Basic mode shows them: they protect the save, and
Basic hides other chrome, not this. The footer is not hidden in Basic today, so the line shows there too.

Only one of 2 and 3 is ever on screen. If both would show, the nudge wins and the hint waits for a later visit.

The line and the nudge both state "N days". That overlap is what ROADMAP asks for ("a 'last backup N days ago' line
with one export nudge"): the line is always there, the nudge is the rare prompt. Both take N from the same helper (§2).

## 2. Wording (exact)

Line (element 1), in `.xfer`, class `backup-line`:

- never exported: `No backup yet.`
- 0 days: `Last backup: today.`
- 1 day: `Last backup: yesterday.`
- 2 or more days: `Last backup: N days ago.`
- 14 days or more: same text, class `stale` (amber text, same as other `--warn` text; no icon, no bold)

**One day count for everything.** A pure helper `daysSince(ms, now)` returns whole calendar days between the two times
in the browser's time zone (local midnight to local midnight). It is the only day count: the line's text, the stale
class, the nudge's 14-day test, the `nudgeAt` 14-day test and the N in the nudge text all use it. So the line turns amber
on the same day the nudge can first show, and both print the same N. No "hours", no weeks or months (one unit keeps it
short and testable). If the clock is wrong (timestamp in the future), `daysSince` returns 0 (`Last backup: today.`).

Nudge (element 2): `You haven't exported a backup in N days. Progress lives in this browser only.` with buttons
`Export progress` and `Not now`. When never exported and the baseline (§3) is 14 days old, the text is
`You haven't exported a backup yet. Progress lives in this browser only.`

Home Screen hint (element 3): `Safari can clear a site's saved data after a week unused. To keep your progress, export
it, then tap Share and Add to Home Screen. The Home Screen copy starts empty: import your file there.` with buttons
`Export progress` and `Got it`.

The last sentence matters if it holds: the hint relies on the Home Screen app having its own storage, so it would not see
the Safari tab's progress, and telling the player to add it without that sentence would look like data loss.

**To verify before build (owner or a permitted source), all three claims are unverified:**

1. "after a week unused" (Safari clears a site's data after 7 days without a visit),
2. "Home Screen apps keep their data much longer" (the premise of the hint),
3. "The Home Screen copy starts empty" (the Home Screen app does not share the Safari tab's storage).

They come from the ROADMAP note and general knowledge, not from a source recorded in `claims.json`. Per the data policy
each is single source until checked. If 1 is not confirmed, drop the number ("Safari can clear a site's saved data").
If 3 is not confirmed, drop the last sentence. If 2 is not confirmed, the hint is not built (the line and nudge still are).

**Checked at build (2026-10-16, #101; robots.txt and terms read first, facts only):**

1. Confirmed by two sources, with a nuance: WebKit, "Full Third-Party Cookie Blocking and More"
   (https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/: script-writable storage, localStorage
   included, deleted "after seven days of Safari use without user interaction on the site") and MDN, "Storage quotas and
   eviction criteria" (https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria:
   the same seven days of browser use, with cross-site tracking prevention on). The count is days of Safari use, so
   "after a week unused" is the soonest it can happen ("can clear" stays). Kept.
2. Confirmed by WebKit (the vendor), same post: Home Screen web apps "have their own counter of days of use" and "We do
   not expect the first-party in such a web application to have its website data deleted"; "Updates to Storage Policy"
   (https://webkit.org/blog/14403/updates-to-storage-policy/) lists being opened as a Home Screen web app as a factor for
   granting persistence. MDN does not cover it. Hint built.
3. Not confirmed: neither WebKit post nor MDN says whether the Home Screen app shares the Safari tab's storage. **The
   last sentence is dropped** as above. Owner check on an iPhone: add the site to the Home Screen from a Safari tab that
   has progress and open it; if it starts empty, the sentence can go back in.

**Existing protection.** `src/site.js` already calls `navigator.storage.persist()` on the standalone site when a save
exists (once per browser session), for the same Safari eviction reason. Whether Safari grants it to a plain tab, and so
how much the hint adds on top, is part of the check for claim 2. The hint does not replace that call; nothing changes there.

## 3. When it shows and hides

All three elements: standalone site only (§1). On the site the Export button (`#expBtn`) is always shown (Blob path), so
"export available" needs no further test.

Element 1 (line): always shown on the site. Updates after an export without a reload.

Element 2 (nudge) shows when all of these hold:

1. The save-failed banner is not showing (that banner already says "Export a backup").
2. The player has progress worth saving: at least one tick (`Object.values(checks).some(Boolean)`) or `level > 1`
   (a fresh browser starts at Lv 1 on the first quest, `src/core/migrations.js`; `DEFAULT()`'s `level: 5` is not the
   fresh start).
3. `daysSince(base, now) >= 14`, where `base` = `backup.lastExportAt`, else `backup.since` (§4). If neither is a
   valid time, no nudge (this cannot happen after `backup1`; the rule only stops a malformed save from nudging at once).
4. `nudgeAt` absent, or `daysSince(backup.nudgeAt, now) >= 14`.

It hides on: a successful export (the line updates, the card goes), `Not now` (sets `nudgeAt = now`; it returns only
after another 14 days without an export), and while the save-failed banner shows.

"One nudge" is read as: never more than one at a time, and never more often than once per 14 days. It does not
come back every visit and it never blocks anything.

Element 3 (hint) shows when all of these hold:

1. iPhone Safari, not already installed: UA contains `iPhone` or `iPod`, contains the `Safari/` token, does not contain
   `CriOS`, `FxiOS` or `EdgiOS` (Chrome / Firefox / Edge on iOS), and `navigator.standalone` is not true. The `Safari/`
   token rules out in-app WebViews (Instagram, Discord, the Google app `GSA/`…), which have no Add to Home Screen.
   iPad is out of scope (ROADMAP says iPhone).
2. The player has progress worth saving (same test as 2.2).
3. `backup.a2hsAt` is absent, and no nudge is showing.

It hides on: `Got it` (sets `a2hsAt = now`, never shown again), `Export progress` (exports, then keeps the card until
`Got it`, since the Share step comes next), and when the page is opened from the Home Screen
(`navigator.standalone`). A player who already added it never sees it, and the hint never re-arms.

## 4. Storage

One optional object on the existing save, no new key:

```json
"backup": { "lastExportAt": 1760000000000, "since": 1759500000000, "nudgeAt": 0, "a2hsAt": 0 }
```

- All fields are epoch ms numbers, all optional. Absent or not a finite positive number = "never".
- Key stays `aion2-assassin-route-v4`; no rename, no version, no second key (CLAUDE.md).
- Written through `storeState()` like everything else. It goes in the top level of the save, not per character, since
  it describes this browser's copy.
- **Not synced, stays local.** `backup1` is not added to `ONE_TIME_FLAGS` (`src/core/sync.js`), and `backup` is not a
  character field, so `merge()` treats both like view settings: each device keeps its own, a later cloud sync neither
  carries nor clobbers them. Recorded here so the 0.6 sync work does not have to guess: a device's backup times say
  nothing about another device's copy.
- `lastExportAt` is set when the export is handed to the browser (Blob path, on click). The browser gives no
  confirmation that the file was kept, so the line says "Last backup", not "saved". The field is stored before the
  file is built, so the file equals the save at the moment of export (owner, 2026-10-16, keeping the `e1` check "export:
  file equals the saved state"); import ignores the file's `backup` (below).
- `since` is the baseline for players who never exported, so "14 days" has a start. It is set by `backup1` (below) or
  by import, and never moved by later writes; it is ignored once `lastExportAt` exists.

**Migration `backup1`** (additive, once, idempotent, leaves old data in place), in `src/core/migrations.js`, run after
the existing steps:

```js
if (!s.backup1) { if (!s.backup || typeof s.backup !== "object" || Array.isArray(s.backup)) s.backup = { since: now * 1000 }; s.backup1 = true; }
```

- It runs for **every** browser, fresh ones included (`hadSave` is not tested), so every save has a baseline and a new
  player is nudged 14 days after their first visit with progress.
- It does **not** call `store()`, like `stampV1`: the field and the flag go out with the next save. On a fresh browser
  that is the first tick; on a saved browser it is the page's start-up write (see golden, §6).
- A `backup` that is already an object is left as it is (no field rewritten, malformed fields just read as "never").
  No other field is touched. An older build that loads the save keeps `backup` and `backup1` (`loadState` lays the save
  over `DEFAULT()` and `storeState` writes the whole object, as for `savedAt` and `mt`).
- `now` is the clock value the migration is given (seconds, `Math.floor(Date.now() / 1000)` in `main.js`); the field
  stores ms so it matches `savedAt`.

**Import.** The file replaces the save, as today. Two additions to the import handler (`main.js`, next to the
`seedLv12 / stTriniel1 / dvReset1` flags it already sets; `migV5`, `eputSync1` and `stampV1` still run on imported
files as before):

- Whatever `backup` the file carries is ignored: import writes `backup = { since: now, lastExportAt: now }` (ms). The
  player evidently holds a file, so the import counts as a backup, and another device's `nudgeAt` / `a2hsAt` do not
  suppress prompts here.
- It sets `backup1: true`, so the migration does not run again on the imported save.

## 5. Accessibility

- The nudge and hint are `role="status"` (polite), not `role="alert"`: they are advice, unlike the save-failed banner.
  They are inserted hidden-then-shown by toggling `hidden` on a container that is always in the DOM, so screen readers
  announce the change.
- Focus is never moved to them. They come right after the header in reading order so keyboard users reach them early.
- Buttons are real `<button type="button">`, 12 px mono like `.xfer-btn`; on touch they get the 44 px target size the
  rest of the page uses (0.1.9). `Not now` and `Got it` have `aria-label`s that name what is dismissed.
- The amber on a stale line is a secondary cue, not the signal: the line's text gives the number of days but not the
  14-day threshold, so a player reads "16 days ago" as information and the nudge is what asks for action. Amber on the
  dark panel is `--warn` text already used elsewhere (contrast checked by the `a11y` suite); the light mockup palette
  uses a darker amber for the same reason.
- The line has no live region (it changes only after the player's own click, and `#xferMsg` already announces export
  results). Text wraps at 390 px and at 200% zoom with no horizontal scroll (see the 390 px screenshots).
- `prefers-reduced-motion`: no animation anywhere.

- `mig1` (`tests/e1-migtest.js`) compares rendered metrics and `checks` / `started` / `areaRun` only, and `journey`
  does not read the save shape. Neither reads `backup` or `backup1`, so they pin nothing here. Still run them (CLAUDE.md:
  any change that could touch saves), expecting no change.
- The pins are the core migrations test (1), `tests/e2-migtest.js` (9) and golden (10).

Node (`tests/core/`, no browser, `node tests/core.mjs`):

1. `migrations.test.mjs`: `backup1` sets `backup = { since: now * 1000 }` for **both** `hadSave` true and false; adds
   only `backup` and the flag (deep-equal of the rest); is idempotent (second run, even with a later `now`, changes
   nothing); leaves an existing `backup` object untouched; replaces a malformed `backup` (string, array, `null`) without
   throwing and leaves malformed fields inside an object (negative, string) as they are; and does not call `store()`

## 7. Out of scope

Anything in the claude.ai build, automatic downloads, cloud backup (0.6 sync), reminders by e-mail or notification, an
Android install prompt, anything about iPad, a light theme, and any wording for other languages.
