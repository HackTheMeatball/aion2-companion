## 1. Goals and non-goals

**Goals (ROADMAP 0.3).**

1. **One evaluator** answers, for every trackable thing, "done?", "open now?", and if not, "what blocks it, and how far
   away is that?". Every card asks it; no card keeps its own gate logic (today: `openSteps`, `rqStatus`, `stigmaSlots`,
   `dvNext`, `SP_STEPS.req`, the story card's `gated`, the Krao Cave special case in `storyCard`).
2. **Blocker chains**: "unlocks after story X · N quests ahead", "needs Lv 27", "after *Blade of Vengeance* is turned
   in", composed when a blocker is itself blocked.
3. **Completion derived from the story position**, never stored as ticks.
4. **Every gate sourced or labelled** (`basis` on every atom; `owner-check` shown as "check in game" where it matters).
5. The **Daevanion boards gated on "Urgent Pursuit"** (one gate on the whole window, inherited by every board, §10), **all 3 specialty slots** at effective skill level 8 / 12 / 20,
   an **Ascension progress bar**, and an **invariant test** over ~10,000 states.

**Non-goals.** Location-aware ranking, the fastest / completionist toggle and catch-up ranking (F1, F10, F15) are 0.4;
the evaluator exposes what they need (§14) but 0.3 keeps today's ranking order. No new save field, no migration. No
Elyos, no second class (the evaluator is class-agnostic, the data is per class).

## 3. The model

**Nodes.** Every trackable thing is a node with an id (data id), a save key where it has one, and a gate:

| Kind | Id / key | `requires` | `completesWith` |
|---|---|---|---|
| story quest | `sq:<game id>` / name | previous quest turned in (+ unlock level, §7) | reaching the next quest (position) |
| Ascension quest | `asc:<slug>` / none | story atom, previous chapter (inferred), gauge (shown only) | its wrapper story quest turned in |
| guide step | `g22:0`, `build:1`, … | milestone level (`rule`) + story / done atoms | `tick`, wrapper, `turnedIn` (byStory) |
| regional quest | `rq:<id>` | unlock level, story atom, regional `done` atoms | `tick` (+ follow-up rule, §5.3) |
| Sealed Dungeon / stronghold | `sd:` / `g10h:` / `sh:` | band level | `tick` |
| plan board node | node key (`dv:…`) | board level, and its board's gate (inherited: `done unlock:daevanion`, §10) | `tick` |
| skill level line | `sp:<skill>:<L>` | `rule:skill-level-gate` (character level) | `tick` |
| specialty slot | `sp:<skill>:spec`, `:spec2`, `:spec3` | effective skill level ≥ 8 / 12 / 20 (§9) | `tick` |
| stigma slot / "put on E" | `g22:1` … / `g27:1` … | slot level + `done g22:0` | equipped (`tick`) / `done` slot step |

**Graph.** `done: X` atoms and derived completions are edges. The generator builds the graph once (at build time,
`GATE_GRAPH`: node → compiled gate) and fails on a cycle, an unresolved reference, a story atom without `is`, or
`done` on a story quest (most of these checks exist since 5b; this PR extends them to proposals and plan nodes).

**Atom semantics** (DATA-FORMAT-V2 §6; `pos` = index of the current quest in the story chain, `-1` if unset or unknown):

| Atom | True when | Blocker when false |
|---|---|---|
| `{level: n}` | `level ≥ n` | `{kind: "level", need: n, have: level}` |
| `{story: X, is: "reached"}` | `pos ≥ idx(X)` | `{kind: "story", quest: X, ahead: idx(X) − pos}` |
| `{story: X, is: "turnedIn"}` | `pos > idx(X)`, or `pos = idx(X)` and `storyEnd = X` | `{kind: "story", quest: X, ahead: idx(X) − pos + 1, turnIn: true}` |
| `{done: Y}` | `done(Y)` (tick or derived) | `{kind: "done", of: Y, chain: blockers(Y)}` |
| `{itemLevel}`, `{player}` (`playerChecked`) | never evaluated | never blocks; returned in `info[]` ("check in game") |
| `all` / `any` | every / at least one | all unmet children / the cheapest branch (fewest blockers); `any` is unused in today's data |

Unset story (`pos = -1`): every story atom is unmet with `ahead: null` ("set your quest"), exactly as today's
`openSteps` / `rqStatus` / `renderStoryChips` behave.

## 4. Outputs and blocker chains

```js
evaluate(char, opts) → Ev             // one pass per update(); memoised per node; pure
Ev.node(id) → {
  done: false | "tick" | "derived",   // derived: which completesWith entry held (e.g. "turnedIn sq:2102185")
  open: boolean,                      // requires met (playerChecked atoms ignored)
  blockers: Blocker[],                // unmet atoms, in display order: story, level, done (empty when open)
  root: Blocker | null,               // the first leaf of the chain: what the player must do first
  info: Atom[],                       // playerChecked atoms (shown, never enforced)
  basis: "sourced" | "owner" | "rule" | "inferred" | "owner-check" | "legacy", // weakest atom basis (label)
  eta: { level?: n, quest?: X } | null // earliest level and story position at which it can open (0.4 catch-up)
}
Ev.list(filter) → nodes in catalog order with the record above (cards iterate this)
```

**Chain rule.** For an unmet `done: Y`, the blocker carries Y's own blockers (recursively, memoised; cycles are
impossible after the generator check). The display uses `root` and the hop count:

- story leaf: `unlocks after "X" · N quests ahead` (`turnedIn`) or `opens on "X" · N quests ahead` (`reached`);
  `N = 0` reads "your current quest" (turn it in);
- level leaf: `needs Lv N`;
- a `done` hop is named when it is the whole story: `after "Blade of Vengeance" is turned in`; two or more hops:
  `after "Blade of Vengeance" (unlocks after "Verdant Melody" · 3 quests ahead)`. One line, no nesting beyond the
  root plus its first hop (minimal visual distraction).

Wording is a UX-pass item (E6 mockup); the data shape above is what this design fixes.

**Cost.** ~450 nodes per evaluation (86 story, 5 Ascension, 58 regional, 60 dungeons, 15 strongholds, 53 steps, 28 plan
nodes, ~140 skill lines and specialty slots). Memoised single pass: target ≤ 2 ms in `update()` (budget 15 ms; checked by the existing
timing check and a paired benchmark, docs/team/tech-lead.md).

## 5. Derived completion

`done(node) = tick(node) || some(non-tick entry of completesWith holds)`. Derived values are computed on every
evaluation and **never written** (DATA-FORMAT-V2 §6; ARCHITECTURE "derived facts are computed, never stored as ticks").

1. **Story quests**: done iff `pos > idx` (or the last covered quest with `storyEnd`), as `turnedIn`.
2. **Wrapper rule** (prereq-gates §5, Metabot): Spread Your Wings → Perceives, Daeva in a Dream → Hears the Voice, A
   Daeva Dreaming Anew → Dreams, Daeva Trapped in a Nightmare → Witnesses. `g22:0` and `g32:dreams` become done when
   their wrapper is turned in (proposals, §7). `g6:0` already behaves so (byStory). `g45:0` waits (§16 Q9).
3. **Regional follow-ups** (prereq-gates §6, end): a follow-up picked up or turned in proves its prerequisite was
   turned in (`rq:2202016` ⇐ `rq:2202017`, …). Recommendation: derive it (display and gating), never write it (Q3).
4. **byStory steps** (`g10:1`, `g12:0`, `g16:0`, `g16:monolith`, `g37:2`): already `completesWith turnedIn`; the
   evaluator makes today's display-only "done once past it" real for counts and tags.

**What the player sees** (E4, visible): a derived-done row shows a ticked, disabled box with "done in the story" as its
accessible name and tooltip; its stored tick (true, false or absent) is left alone. Un-ticking a derived row is not
possible (the box is disabled); a stored `false` is ignored while the derivation holds and becomes visible again if the
player moves the story back. Milestone counts and tags count derived as done.

## 6. Saves (untouched)

- **No new field, no migration, no write.** The evaluator reads `char(state)`; derived completion is never stored.
  The storage key, item keys and the save shape stay as they are, so a 0.2 build reads a 0.3 save unchanged and the
  5c rollback re-stamp is not exercised by 0.3 at all.
- **New keys only on a tick.** `sp:<skill>:spec2` / `:spec3` (reserved in DATA-FORMAT-V2 §3) are written only when the
  player ticks slot 2 / 3; an older build ignores unknown keys (it keeps them, it saves the whole object).
- **`storyEnd`** keeps its meaning (the last covered quest turned in). Adding "Daeva Trapped in a Nightmare" later moves
  `STORY_END`; a save with `storyEnd = "Forgotten Commander"` then reads as "on Daeva Trapped" through the `turnedIn`
  rule, so no migration (prereq-gates §7). That step waits for owner decision Q7 (§16).
- **Acceptance on every build step**: `mig1`, `mig2`, `journey` green; `golden` `store` field (stored state after
  load) identical for every one of the 2,000 states, even where Next up changes. A step that changes `store` is wrong.

## 7. The gates in the data (this PR)

The audit's gates are loaded into the v2 data now, so the evaluator build steps change code only. Two places:

- **Live fields** (`requires` / `completesWith`) keep exactly what the 0.2 app does. This PR adds there only what
  changes nothing: the unlock-level atoms of Finding Nemon (10) and Forgotten Commander (45), which equal their
  recommended level (what the story card gates on today), and sources on atoms that were `legacy` (the wrapper pages:

## 9. F3: specialty slots 1–3

**Rule (owner F4, data `rule:specialty-slots`).** 3 slots per active skill, open at **effective** skill level 8, 12, 20;
the 5 choices are available at effective 8, 8, 8, 12, 16. **Effective level** = highest ticked `sp:<skill>:<L>` (1 if
none) + one per owned board node whose `skill` is this skill (`adds`, 1 for every Assassin node).

**Evaluator.** A rule node per (skill, slot): open iff effective ≥ the slot's level (the slot alone; a missing pick
never keeps it shut); the *recommendation* names the build's pick for that slot only when the pick exists and its
choice is available at that effective level, else "pick a specialty"; done iff `sp:<skill>:spec` / `:spec2` / `:spec3` is ticked. Replaces the `L === 8`,
`learn + 18` line in `src/data/build.js` (bug F3). Specialty stays free (no points).

**What changes (golden, owner approval):** slot 1 appears when effective 8 is reached, which is the same moment as
today for a player with no board node on that skill (buying level 8 needs `learn + 18`) and earlier with one;
slots 2 and 3 are new cards and Skills-card rows.

**Data gaps (Data & Research; listed for the owner, not guessed):**

- `builds.json` has **one** specialty pick per skill. Slots 2 and 3 need picks from two agreeing sources (or the
  `single-source` label). Until then the slot is shown as "slot 2 open: pick a specialty" with no recommendation.
- Board nodes per Assassin skill: 4 (one per board), so points (max 10) + nodes give **at most 14**: slot 3 (20)
  cannot open from what the app tracks inside Lv 45. The owner's screen (Quick Slice 10 (+3) = 13) fits that. Either
  something else raises skill level (gear?) or slot 3 is an endgame slot. See Q5.
- Only **plan** nodes have save keys; a node the player bought off-plan is invisible, so effective level can
  undercount (never overcount). Recommendation: accept for 0.3 (the guide recommends the plan); custom builds (0.4+)
  add the rest.

## 10. Daevanion gate

Owner screen (`owner:2026-10-14-unlocks-03`, already `unlock:daevanion`): the Daevanion window stays locked until
"Urgent Pursuit" is completed; DECISIONS 2026-10-14 puts the gate in 0.3. **One gate, defined once**: the live

(`rule:crystals-per-level`); only spending waits.

predates the owner screen); no text change.

## 12. The invariant test (~10,000 states)

New suite `invariant`, Node only (no browser, so 10,000 states fit in < 30 s).

- **States**: the golden generator (`tests/golden/states.js`) exported for Node: its 2,000 states plus the 6,000
  extended random ones (`--all`), plus 2,000 targeted ones: every story position × {unlock level − 1, unlock level,
  45} × {no ticks, all ticks, ticked-but-derived-false (stored `false` on derived items)} × Basic / Advanced, and
  board/skill edge cases (effective level 7 / 8 / 11 / 12, Urgent Pursuit open / turned in at Lv 12 and 13).
- **Oracle**: a second, deliberately naive evaluator in `tests/support/oracle.mjs`, written straight from the
  DATA-FORMAT-V2 §6 table over the raw v2 JSON (not the compiled graph), so the test does not grade the engine with
  itself. It takes the same `apply` set as the evaluator and reads `proposed` for those records, so an `--explain`
  run with a proposal on is checked against the gate it applies, not the old one.
- **Invariants** (each failure prints the state id and the card):
  1. Next up never offers (a card with an action) a node whose oracle status is blocked.
  2. Next up never offers a node that is done (ticked or derived).
  3. Every Ascension step whose `requires` holds and that is not done is the first step card (owner rule).
  4. Monotonic: raising the level or advancing the story never closes an open node except by making it done.
  5. Blocker text is consistent: `ahead` equals the oracle's distance; a `level` blocker never shows when level is met.
  6. Saves: `evaluate` never mutates its input (deep-frozen character).
- **Browser cross-check** (in `golden`): for its 2,000 states the page's Next up equals `rankNext` in Node (already
  true by construction; the check keeps the page wiring honest).
- Replaces `tests/golden/violations.js`'s inferred gate table (`KNOWN-VIOLATIONS.md` stays at 0 and is then generated
  from the oracle).

## 13. Golden-master differences for owner approval

Every build step that changes behaviour is gated on a reviewed list, not on a bare re-record:

1. The evaluator has a switch per proposal (`opts.apply = Set<record id>`) and per rule change (`derived`, `f3`).
   A proposal names the rule switches it needs (the `g22:0` / `g32:dreams` completions need `derived`) and turning it
   on turns those on. The golden runner gets `--explain`: it records the step's build with all of its changes on, then
   each change alone (with its required rules), and **attributes every changed state to the smallest set of changes
   that reproduces it** (singles first, then pairs; a step has few enough changes for that to stay cheap). An
   unattributed difference fails the run (it is a bug, not a product change).
2. Output: `tests/out/golden/explain.md`, copied into the PR as a table: change · record(s) · `change` text from the
   data · states affected (by group / level band) · one before / after sample (Next up titles, milestone tag).
3. The owner approves per row (PR checklist). Only approved rows are applied; the snapshots are then re-recorded with
   `node tests/golden.js --record` and committed with the change, and the row's proposal moves into the live fields
   (data diff in the same PR).
4. `store` differences are never approvable (§6).

## 14. Hooks for 0.4 (location-aware Next up; not built)

The evaluator answers *whether*; ranking (`rankNext`) answers *in which order*. 0.4 changes only ranking:

- `Ev.list()` gives every open node with its `route` (`core` / `filler` / `completionist`, DATA-FORMAT-V2 §6), its
  zone (record `location.zone`; Ascension nodes have none) and `eta` (§4), which is what F1 catch-up ("what can I do
  now with my level and points") and F10 level bands need.
- Last confirmed location is `lastConfirmedLocation(char)` (`src/core/sync.js`, from `mt`), already skipping Ascension
  steps; F15's tie-break is a comparator in `rankNext` over `Ev.list()`.
- Kibelisk unlocks (owner: derived from ticks) are another derived fact of the same kind: a later evaluator rule, no
  state.

## 16. Assumptions and open questions

Assumptions (called out; each is checked by a test where possible):

- **A1** The story is linear (one predecessor each, prereq-gates §4); `pos` is an index. The generator already checks one
  path. A branch would need `any` in `requires` (schema allows it; the evaluator implements it; no data uses it).
- **A2** Levels never go down in game; the app's − / slider can lower them, and the evaluator simply re-evaluates (no
  stored result to invalidate).
- **A3** A stored tick on a derived item is the player's intent for when the derivation stops holding (story moved
  back); it is neither deleted nor overridden.
